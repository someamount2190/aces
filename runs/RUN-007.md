# RUN-007 — does the system evolve?

**Date:** 2026-10-29, 20:03–20:20 (Asia/Taipei)
**Label:** subagent-embodied. Generator and Integrator acted; Adversary and Observer were staged but never
reached the challenge, because it was never published.

## What happened

| Turn | Role | Action |
|---|---|---|
| 1 | Generator | registered `carry_chain_roundrobin_1` — 11 steps, four key ops, one `chain_add`, one `chain_xor`, non-affine |
| 1 | Integrator | **rejected** it, with a worked attack: byte 0 has no cross-byte input, so `ct[0]` fixes `k0` in ≤256 trials, then `k1..k3` follow — ~2^10 for the whole key |
| 2 | Generator | **declined to propose again**, with a proof that no program in the op set escapes this |
| — | Adversary | never dispatched; no challenge existed |
| — | Observer | never dispatched; nothing to find |

Final state: 1 candidate, 0 challenges, 0 breaches, 0 candy.

## The finding

The Generator's proof, restated:

> Every op is either per-byte keyed with `k(i)`, per-byte unkeyed, or a forward chain. Therefore output
> byte `i` depends only on plaintext bytes `0..i` and key bytes `K[0..min(i,3)]`. Byte 0 is a per-byte
> function of `pt[0]` and `K0` alone, so one known pair yields `K0` in 256 trials; each further byte
> follows. Total work is `4 × 256 = 2^10`, for **every** program the op set can express.

This is correct, and it invalidates the number the Integrator gates on: `known_plaintext_work` was
`2^key_bits`, which is true only if the key cannot be attacked one byte at a time. With a positional key
schedule and causal chaining, it can.

So the system did evolve — into a stop. Two agents, independently, agreed that the construction space is
exhausted: one found the attack, the other refused to build against it. That is a better outcome than
another five runs of trivially broken ciphers.

## What it changes in the engine

`assess()` now reports the causal bound rather than the key space: `known_plaintext_work` is
`min(2^key_bits, key_bytes × 256)` while every op is causal, with `causal: true` alongside it. The gate no
longer needs an agent to notice the structure — every candidate in the current VM measures 1,024 (32-bit
key) and is refusable on the number alone.

## What would escape it

The proof names the escape routes, and only one of them is real:

| Suggested | Verdict |
|---|---|
| longer key | **does not help** — the attack recovers key bytes positionally, so width is irrelevant |
| non-positional key schedule | helps: byte 0 would depend on more than `K0` |
| backward or circular chaining | helps: breaks the forward-only causality |
| an op that mixes positions both ways | helps, and is the smallest version of the previous row |

The missing capability is a **diffusion operation** — a buffer rotation or permutation that carries data
from later positions back to earlier ones. `DIFFUSION_OPS` exists in `verify.py` and is empty, which is
precisely why every construction is trivial. Adding one op to that tuple turns the causal bound off and
makes the key-width number real.

## Honest summary

The system did what it was built to do: it produced a construction, judged it, rejected it with a reason,
and — when the reason proved to be a theorem about the whole op set — stopped instead of generating noise.
The bottleneck is now structural and named, not hidden in a parameter.
