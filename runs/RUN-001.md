# RUN-001 — first subagent-embodied cycle

**Date:** 2026-10-29, 18:52–19:05 (Asia/Taipei)
**Label:** subagent-embodied. No provider model was used.
**Database:** `runs/run-001.sqlite3` (git-ignored); prompts per tick in `runs/tick-*.json`; answers in `runs/answers/`.

## Setup

Five persistent sessions over one model: generator, integrator, adversary, observer, and a supervisory
warden. Each received only its charter and then one environment payload per dispatch. The coordinator ran
as the `aces.pump` CLI; the orchestrator (a separate agent) carried prompts to sessions and returned
`{"tool":...}` answers. No role was told the project path, the database path, or of the others' existence.

**The full evolutionary cycle ran end to end**: a live model proposed a construction, another published it,

once, the Observer recorded an evidence-linked finding, and the Integrator escalated only because the
previous challenge was BREACHED.

A clean negative result worth recording: the integrator **never** attempted to publish before the breach.
Its charter told it to wait, and the gate would have refused it, so this is policy and constraint agreeing
rather than one of them being tested.

## Harness defects found by running it

1. **The environment exposes bookkeeping the tool rejects.** Catalog entries include `status`,
   `security_claim`, `dependencies`, `keygen`, `input_size`, `test_vector`; `register` accepts exactly five
   fields. The generator copied the visible record and lost a turn to `ValueError`. Fix: project only the
   contract fields into the catalog — the ledger should show what a role may use, not how it is stored.
2. **Payloads are relayed by a human-scale process.** Prompts were pasted by hand; one was mistyped at
   tick 1 (an empty event list instead of one event), the session was discarded and restarted. Fidelity
   here is luck, not design. Fix: the driver should hand the session the exact string from
   `dispatches.projection`, never a re-typed copy.
3. **Observer payload grows with the whole event log.** 4.6 KB by turn 5, re-sending history every turn.
   Fix: send events since the role's cursor.
4. **The Warden's ledger view was 42 KB and had to be capped** to the last 4 dispatches (18 KB). It was
   therefore **not exercised in this cycle** — the only role that did not act. Fix: bound and summarise the
   ledger, and give the warden a diff of what is new since its last pass.
5. **Tool results must be relayed back** (compute → solutions → submit) or the role cannot continue. The
   session only knows what it is told; the message history in `sessions.messages` is the record, not a
   channel.

## What this does and does not establish

- **Establishes:** the four-role loop, the breach gate, exactly-once candy, sanitized failure reporting,
  breach-gated escalation, and the Observer feedback path all work with real agents producing real answers.
- **Does not establish:** autonomy (every tick needed an orchestrator turn), independence (four contexts
  over one model), isolation (no container; blindness is by information withholding), or anything
  cryptographic — an 8-bit key falls to 256 trials, and both the generator and the observer said so first.
- **Not evidence of:** novelty, security, or improvement. The successor challenge is a different
  construction, not a demonstrably stronger one.
